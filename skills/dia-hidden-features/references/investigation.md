# Investigate a new hidden setting

1. Record the installed app version/build from `Contents/Info.plist`. Identify the requested UI and whether it is already available. Establish the smallest observable success condition before editing.
2. Inspect the installed AppleScript dictionary (`Contents/Resources/Dia.sdef`) for a supported operation. The examined dictionary did not offer a general settings API; recheck if the installed app changes.
3. Inspect relevant app resources, framework names, and narrowly filtered binary strings for the UI label, service, flag, preferences key, or serializer. Use `rg` for text resources and `strings` for binary candidates. Avoid dumping all preferences, browsing data, or account state.
4. Trace the consumer of a candidate with static symbol/disassembly tools when needed, such as `nm`, `otool`, or LLDB loading an executable without attaching to a process. Distinguish the service controlling the UI from dormant/legacy clients. Record build-specific evidence and its limits. Addresses and symbol offsets are not portable across releases.
5. Establish the representation and lookup path: macOS defaults, an encrypted key/value store, a startup argument, or remote evaluation. A parser alone does not prove the runtime calls it. `feature-flags` handles only the validated macOS override preference; do not use it to manufacture arbitrary database entries.
6. For encrypted settings, inspect with `dia-tools stores`, `sql-schema`, and `settings get` on temporary snapshots. Use the `dia-settings` workflow for a proven existing key and encoding. Do not guess booleans from BLOB lengths or bypass normal Keychain authorization. Keep root keys and decrypted stores out of logs, process arguments, and source control.
7. Form one evidence-backed candidate, preserve the original state, plan a scoped edit, apply after normal shutdown, and check both persistence and the actual UI after restart. A failed candidate should be removed or restored before the next experiment. If evidence points to server authorization, missing implementation, or an unknown serializer, report the limitation rather than claiming local enablement.

This workflow uses supported local storage mechanisms and static inspection. It does not require patching the app binary, disabling code signing or SIP, injecting code, or modifying remote feature-service caches. Such changes are outside this skill's workflow.
